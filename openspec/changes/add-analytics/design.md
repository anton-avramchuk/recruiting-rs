## Context

Данные для аналитики уже есть: отклики (`applications`), их история (`application_events`), проекция людей с источником (`people`), вакансии. Не хватает одного: чтобы честно посчитать воронку, нужно знать, **какие этапы отклик проходил**, а не только где он сейчас. Сейчас в событиях перевода этап хранится только в тексте («Этап → Скрининг»), что неудобно и хрупко для вычислений. Остальное — вопрос запросов и экрана.

## Goals / Non-Goals

**Goals:**
- Метрики как чистые функции над простыми «фактами» об откликах: легко проверять модульными тестами без БД.
- Один запрос фактов за период и один запрос по неделям; без хранения агрегатов и без фоновых задач.
- Воронка по истории переходов, а не по текущему этапу.

**Non-Goals:**
- Сравнение периодов, экспорт, фильтры по вакансии/рекрутеру, библиотеки графиков, причины отказов, стоимость найма.
- Предварительно рассчитанные витрины (на текущих объёмах считаем по запросу).

## Decisions

**Этап в событиях.** Миграция `0002` добавляет `application_events.stage text` (допустимые ключи этапов, `NULL` для событий без этапа) и заполняет его по существующим записям: для `kind = 'stage'` — по тексту «Этап → <название>» через `CASE` по восьми названиям, для `kind = 'rejected'` — `'rejected'`. Домен: `NewEvent` получает необязательный `stage`; `move_to` и `reject` пишут его. Создание отклика на «Новый» своего этапа не пишет — начальный этап «Новый» учитывается всегда. Альтернатива «разбирать текст событий при каждом запросе» отклонена: ломается при смене формулировок. Альтернатива «отдельная таблица переходов» избыточна: события уже существуют и хранят время.

**«Дошёл до этапа».** Для отклика считается порядковый номер самого дальнего этапа воронки (`new`=1 … `hired`=7), которого он достиг: максимум по событиям с этапом из линии воронки и текущего этапа (если он в линии). Отказ в линию не входит. Отклик учитывается на всех этапах от первого до достигнутого. Конверсия этапа = достигших этап / достигших предыдущий, округление до целого процента; для первого — 100; при нуле в знаменателе — 0. Этап наибольшей потери — минимальная конверсия среди этапов 2…7, если она меньше 100 и откликов больше нуля (при равенстве — более ранний этап).

**Факты и расчёты.** Модуль `domain::analytics` содержит `AppFact { created_at, stage, stage_changed_at, source, reached, first_touch }` и функции `funnel`, `median`, `time_to_hire_days`, `first_touch_hours`, `sources`, `weeks`. Хранилище отдаёт факты одним запросом за период (`created_at >= now - days`), `reached` и `first_touch` берутся коррелированными подзапросами по `application_events` (индекс по `application_id` уже есть). Срок найма: `stage_changed_at - created_at` для откликов на «Выход» (этап менялся в момент выхода). Первое касание: минимальное время события с `kind <> 'created'` минус создание.

**Динамика и повторные кандидаты.** Недели — отдельный запрос по `date_trunc('week', created_at AT TIME ZONE 'UTC')` за последние 12 недель (понедельник — начало недели), недостающие недели заполняются нулями в домене. Повторные кандидаты — `count` людей с более чем одним откликом по всей организации.

**Источники.** Источник берётся из проекции `people.source` (пусто — «Не указан»); дошедшие до интервью — `reached >= 3` («Интервью HR»). Сортировка: конверсия по убыванию, затем число откликов по убыванию, затем название.

**Нагрузка на вакансии.** Используется существующий список вакансий (приоритет, срок открытия) с числом активных откликов.

**API.** `GET /analytics?days=90` → `AnalyticsDto`: `period_days`, `funnel` (этап, достигли, конверсия), `worst_stage`, `median_days_to_hire`, `median_hours_to_first_touch`, `repeat_people`, `weekly` (`week_start`, `count`), `sources`, `vacancies`. Права — чтение; `days` вне 7…365 — 400. Перед расчётом проекция людей синхронизируется (как у остальных чтений).

**Экран.** Страница `/analytics` в `web-crm`: `Resource` по периоду (переключатель 30/90/180/365), столбцы недель и полосы воронки рисуются `div`-ами с шириной/высотой в процентах (без библиотек), таблица источников, список вакансий. Этап с наибольшей потерей выделяется подписью и жирным начертанием; цвет сигнала только для давно открытых вакансий. Данные запрашиваются через `ui_kit::api::call` (браузер → BFF, SSR с данными).

## Risks / Trade-offs

- [Старые события без этапа при неполном заполнении] → миграция заполняет по тексту, неопознанные остаются `NULL`; воронка тогда опирается на текущий этап (нижняя оценка), что отражено в расчёте «максимум».
- [Расчёт по запросу на больших объёмах] → один запрос по индексам организации за ограниченный период, расчёт в памяти; при росте объёмов добавится материализация (вне этого change).
- [Время UTC для недель] → для рекрутеров в других поясах граница недели сдвинута; допустимо, указано в спеке.
- [Выход считается по `stage_changed_at`] → перевод из «Выход» назад и обратно сбрасывает момент; это отражает последний выход.

## Migration Plan

Миграция аддитивна (столбец и заполнение); эндпоинт новый. Откат — вернуть предыдущий образ: столбец безвреден.
