## Context

`identity` хранит пользователей тенанта (`users`, RLS), `UserService` умеет `list/create/update`; `PATCH` меняет роли, статус и имя, блокировку себя запрещает. Право `ManageUsers` только у `owner`. Refresh-токены лежат в `refresh_tokens`, есть `revoke_all_for_user`. Access-токены короткоживущие и содержат роли. BFF уже пропускает `/users`. Фронтенд общается только с BFF через `ui_kit::api::call`; видимость экранов по ролям определяется по `SessionCtx` (как `can_write`).

## Goals / Non-Goals

**Goals:** экран управления командой для владельца; невозможность остаться без владельца; сброс пароля и отзыв сессий.
**Non-Goals:** приглашения по email и самостоятельная смена пароля пользователем; журнал аудита; кастомные роли; удаление пользователей (только блокировка); немедленный отзыв уже выданных access-токенов.

## Decisions

- **Инвариант владельца в сервисе**: `update` в одной транзакции блокирует строки активных владельцев (`SELECT ... WHERE 'owner' = ANY(roles) AND status='active' FOR UPDATE`), применяет изменение и, если активных владельцев не осталось, возвращает `Conflict` (409, «организация должна иметь активного владельца»). Блокировка нужна, чтобы две параллельные операции не оставили 0 владельцев. Блокировка себя остаётся отдельной ошибкой.
- **Пароль в `PATCH /users/{id}`**: необязательное поле `password`, та же проверка длины, что при создании (400), хеш через `platform_auth::password`; доступно `owner` для любого пользователя своего тенанта, включая себя.
- **Отзыв сессий**: если запрос меняет роли, блокирует пользователя или меняет пароль — в той же транзакции вызывается `refresh_tokens::revoke_all_for_user`. Разблокировка и правка имени токены не трогают.
- **Экран `/team`** в `apps/web-crm/src/team/` (`server.rs` — серверные функции, `view.rs`). Таблица: имя, email, роль (select), статус, действия «Заблокировать/Разблокировать», «Сбросить пароль» (встроенная форма), правка имени. Форма создания над таблицей. UI пишет роль списком из одной роли; пользователь с несколькими ролями показывается как есть, пока владелец не выберет роль.
- **Доступ в интерфейсе**: пункт «Команда» и переход из палитры только при роли `owner` (по `SessionCtx`); у остальных `/team` показывает «Нет доступа». Окончательно права проверяет API (403).
- **Ошибки**: 409/400 отображаются у формы или строки с понятными текстами, значение в списке остаётся прежним.

## Risks / Trade-offs

- Начальный пароль знает владелец, а не пользователь — без почтовой инфраструктуры приемлемо; смены пароля пользователем нет.
- Access-токен заблокированного пользователя работает до истечения срока (минуты).
- Блокировка строк владельцев при каждом изменении — нагрузка пренебрежимо мала.
