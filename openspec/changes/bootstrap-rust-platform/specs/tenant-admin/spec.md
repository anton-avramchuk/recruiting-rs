## ADDED Requirements

### Requirement: Реестр тенантов
Система SHALL вести реестр тенантов с уникальным slug, названием и статусом (`active`, `suspended`). Операции доступны только платформенным администраторам.

#### Scenario: Создание тенанта
- **WHEN** администратор создаёт тенанта с уникальным slug и данными первого владельца
- **THEN** тенант создаётся в статусе `active`, а в identity создаётся пользователь с ролью `owner`

#### Scenario: Дублирующий slug
- **WHEN** администратор создаёт тенанта с уже занятым slug
- **THEN** возвращается 409, тенант не создаётся

#### Scenario: Сбой провижининга
- **WHEN** создание первого владельца в identity не удалось
- **THEN** тенант не остаётся в реестре в активном состоянии

### Requirement: Приостановка и активация
Администратор SHALL иметь возможность приостановить и вновь активировать тенанта. Приостановка MUST блокировать новые входы и обновление токенов пользователей тенанта; данные тенанта не удаляются.

#### Scenario: Приостановка
- **WHEN** администратор приостанавливает тенанта
- **THEN** вход и refresh его пользователей отклоняются, данные сохраняются

#### Scenario: Активация
- **WHEN** администратор активирует приостановленного тенанта
- **THEN** пользователи снова могут входить

### Requirement: Просмотр тенантов
Администратор SHALL получать постраничный список тенантов с фильтром по статусу и поиском по названию или slug.

#### Scenario: Фильтр по статусу
- **WHEN** запрошены тенанты со статусом `suspended`
- **THEN** возвращаются только приостановленные
