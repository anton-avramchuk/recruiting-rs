# Design

## Context

Весь общий интерфейс лежит в `crates/ui-kit` (≈2600 строк: API-клиент, сессия, оболочка, тема, `Grid`), а повторяющиеся куски живут в `apps/web-crm` (≈10 тыс. строк) и `apps/web-admin`. Наблюдаемое сейчас:

- `Reply<T>` и `classify` определены в `web-crm/src/funnel/server.rs`, но используются в `clients`, `security`, `comments`; в `candidates/outcome.rs` пять собственных `*Outcome` и `classify_*`, в `web-admin/tenants.rs` — `CreateOutcome`/`StatusOutcome`; тексты ошибок переводятся в трёх `failure_text`.
- Списки `persons`, `clients`, `tenants` уже постраничные (`page`, `page_size`), но без сортировки и фильтров; схему `platform-grid` имеет только список пользователей identity.
- `GridUrl`, `FilterSpec`, `page_info`, `RowActions` в `ui-kit/grid` не используют Leptos, то есть уже являются логикой `ui-core`.
- Образец структуры — `E:\Projects\cheetahrc\wasm`: `ui-core` (поведение без вёрстки), `ui` (контролы), `front-data` (`EntityGrid`, `CrudUi`), `check-boundaries.py`, витрина `showcase`.
- Для SSR+hydrate (cargo-leptos) крейты с компонентами несут фичи `ssr`/`hydrate`, как сейчас `ui-kit`. Уроки: `Resource` вне `Suspense` зависает при SSR (использовать `LocalResource`); `Transition` вокруг `Grid` ломает фильтры.

## Goals / Non-Goals

**Goals:**
- Приложение собирает экран из готовых компонентов, не повторяя пейджер, диалоги, цепочки команд и перевод ошибок.
- Крейты можно взять в другую систему: общие слои не знают о рекрутинге.
- Каждая волна завершается зелёной регрессией и отдельными коммитами; поведение интерфейса не ломается.

**Non-Goals:**
- Переход на CSR/Trunk или смена Leptos, переписывание бэкенда сверх схем списков.
- Новые экраны и функции; перевод остальных списков (вакансии, доска) на грид.
- Публикация крейтов в реестре.

## Decisions

- **Раскладка крейтов** (по `cheetahrc`): `ui-core` (чистый Rust, без `leptos`), `ui` (контролы), `ui-data` (`Query`, `Mutation`, `EntityGrid`), `ui-shell` (оболочка, сессия, вход, запуск), крейты блоков `ui-security`, `ui-comments`, `ui-palette`, `ui-import`. Отказ от одного крейта с модулями: границы проверяются по зависимостям Cargo, а `ui-core` остаётся быстро тестируемым нативно.
- **Миграция постепенная (strangler):** `ui-kit` сначала становится фасадом с `pub use` новых крейтов, чтобы приложения переходили по одному экрану; в конце волны 3 фасад и крейт удаляются. Альтернатива «большим взрывом» отвергнута: слишком длинный период без зелёных e2e.
- **`Reply<T>` в `ui-core`** с serde (пересекает границу server fn). Особые исходы выражаются данными: вариант `Conflict` получает необязательные детали (найденный дубль кандидата), чтобы `CreateOutcome::Duplicate` стал `Reply::Conflict` с данными. Тексты ошибок — одна функция перевода по коду и сообщению BFF; специфичные конфликты (`"Роль с таким названием уже есть"`) передаются таблицей контекста, а не отдельными функциями.
- **`Query` и `Mutation`** тонкие обёртки над `LocalResource`/`Action`: `Query` не использует `Resource` вне `Suspense` (риск зависания SSR), поэтому данные, зависящие от клиента, грузятся на клиенте; страницам, которым нужен SSR, остаётся прямой `Resource` в `Suspense` — `Query` это допускает параметром.
- **Диалоги:** один `Dialog` с управлением фокусом (фокус на безопасной кнопке, возврат на вызвавшую), `ConfirmDialog` и `Drawer` строятся на нём; палитра и шпаргалка переходят на `Dialog`. Нативный `<dialog>` не берём из-за расхождений в SSR; роль `alertdialog`/`dialog` и `aria-modal` задаём сами.
- **Серверные схемы списков:** `GridSchema` для `persons` (candidate), `clients` (client), `applications` (recruitment), `tenants` (admin); поля — белый список, значения параметрами, RLS через `TenantTx` (для `tenants` — таблица платформы без RLS, доступ только администратору). `page`/`page_size` остаются, `sort`/`filter` добавляются; BFF пробрасывает параметры и расширяет allowlist.
- **CSS:** `ui-core` стилей не имеет; `ui` несёт токены и стили контролов (`style/ui.css`), блоки — свои файлы; доменные стили воронки, «Сегодня», разбора, импорта и аналитики переезжают в `apps/web-crm/style/`. Подключение — через компонент стилей каждого крейта, как сейчас `UiStyles`.
- **Проверка границ:** скрипт на Python (`check-boundaries.py`, как в `cheetahrc`) читает `cargo metadata` и сверяет зависимости с таблицей слоёв; запускается локально и в CI позже (CI сейчас не делаем).
- **Витрина:** отдельное приложение `examples/showcase` (SSR/hydrate) с примерами и таблицами свойств; собирается в рабочем пространстве, но не входит в Docker-стек.
- **Порядок внутри волн:** сначала чистая логика в `ui-core` с тестами, затем контролы, затем перевод экранов, затем удаление старого; e2e по затронутым страницам после каждого перевода.

## Risks / Trade-offs

- **Объём:** изменение велико. Смягчение: три волны, фасад `ui-kit`, коммит после каждой группы задач, полный e2e в конце волны.
- **Время сборки и память:** больше крейтов в cargo-leptos; прогон e2e тяжёлый (раньше обрывался по памяти). Смягчение: запуск e2e по файлам и с ограничением потоков.
- **Гидрация:** перенос компонентов может ввести расхождения SSR/hydrate. Смягчение: e2e с перезагрузкой страницы у каждого грида.
- **Совместимость API списков:** изменение схем затрагивает 4 сервиса и BFF. Смягчение: параметры только добавляются, прежние запросы работают (тесты).
- **Единый `Reply`** меняет сигнатуры server fn: правка всех экранов и тестов; делается экран за экраном вместе с переводом.
- **Тест «красным вперёд»:** для чисто визуальных контролов опора на e2e и юнит-тесты логики в `ui-core`; визуальные дефекты ловятся витриной и ручным просмотром.
