## Purpose
Состояние данных экранов на сигналах: чтение (`Query`), команды (`Mutation`), сетка записей (`EntityGrid`) и единый исход обращения к серверу.

## ADDED Requirements

### Requirement: Единый исход обращения
Исход обращения к серверу SHALL описываться одним типом `Reply<T>`: успех, ошибка проверки с полем и сообщением, конфликт, нет доступа, не найдено, сервис недоступен. Преобразование ответа BFF в `Reply` (`classify`) и перевод сообщений для пользователя MUST находиться в `ui-core`. Отдельные `Outcome`-типы по сущностям (кандидаты, тенанты) MUST NOT остаться; особые исходы (например, найденный дубль при создании) выражаются данными в варианте `Reply`.

#### Scenario: Перевод ответа
- **WHEN** BFF отвечает 404, 403, 409 либо 400 с полем
- **THEN** `classify` возвращает соответствующий вариант `Reply`, а сообщение для пользователя по-русски формируется в одном месте

#### Scenario: Один тип на все экраны
- **WHEN** экран кандидатов, заказчиков, тенантов или безопасности вызывает серверную функцию
- **THEN** результат — `Reply<T>`

### Requirement: Чтение данных (Query)
Компонент `Query` SHALL заменить связку «ресурс, ожидание, ошибка, пусто»: показывает индикатор загрузки, при успехе — переданное представление, при `Reply` не-успехе — сообщение об ошибке единым видом, при пустом результате — `EmptyState`. Прежние данные остаются на экране, пока идёт повторная загрузка. Повторная загрузка запускается изменением ключа или командой `reload`.

#### Scenario: Загрузка и ошибка
- **WHEN** запрос выполняется либо завершился ошибкой
- **THEN** показан индикатор загрузки либо сообщение об ошибке без падения страницы

#### Scenario: Перезагрузка
- **WHEN** после команды вызывается `reload`
- **THEN** данные перечитываются, прежнее содержимое остаётся до ответа

### Requirement: Команды (Mutation)
Компонент состояния `Mutation` SHALL выполнять команду над сущностью: хранить признак «идёт», при успехе вызывать переданное действие (сообщение, перезагрузка списка, переход), при ошибке — показывать сообщение из `Reply` либо запасной текст. Один и тот же `Mutation` MUST использоваться для сохранения форм, удаления и смены статуса вместо ручной связки `Action` и `Effect`.

#### Scenario: Успех
- **WHEN** команда выполнена успешно
- **THEN** вызвано действие успеха, признак «идёт» снят

#### Scenario: Ошибка
- **WHEN** команда завершилась `Reply` не-успехом
- **THEN** сообщение показано пользователю, введённые данные формы не потеряны

#### Scenario: Двойной запуск
- **WHEN** команда уже выполняется и запускается ещё раз
- **THEN** повторный запуск игнорируется, пока первый не завершится

### Requirement: Сетка записей (EntityGrid)
`EntityGrid` SHALL объединять `Grid` с командами над записью: удаление с подтверждением через `ConfirmDialog`, перечитывание страницы после команды, правила видимости действий. Экраны списков MUST собираться из `EntityGrid` и описания столбцов, не содержа собственной логики страниц, сортировки и фильтров.

#### Scenario: Удаление записи
- **WHEN** пользователь подтверждает удаление в строке
- **THEN** команда выполнена, текущая страница перечитана

#### Scenario: Экран списка
- **WHEN** добавляется новый список сущности
- **THEN** он описывается столбцами и функцией загрузки, без собственного пейджера
