## ADDED Requirements

### Requirement: Обращения к BFF из браузера
После гидратации фронтенд SHALL отправлять запросы за данными, вход, выход и изменения из браузера напрямую в BFF по публичному адресу, с cookie сессии (`credentials: include`) и CSRF-токеном, полученным от BFF; промежуточные server functions сервера фронтенда для этих целей не используются. Первая отрисовка на сервере MUST содержать те же данные: сервер фронтенда запрашивает BFF по внутреннему адресу с cookie входящего запроса, одной и той же функцией доступа, что и браузер. Ответ BFF с кодом 401 в браузере ведёт на экран входа.

#### Scenario: Изменение данных без перезагрузки
- **WHEN** рекрутер переводит отклик на другой этап
- **THEN** браузер отправляет запрос на публичный адрес BFF с заголовком `x-csrf-token`, а страница обновляется без перезагрузки

#### Scenario: Первая отрисовка с данными
- **WHEN** авторизованный пользователь открывает страницу напрямую по адресу
- **THEN** HTML, пришедший с сервера, уже содержит данные страницы

#### Scenario: Сессия истекла
- **WHEN** BFF отвечает на клиентский запрос кодом 401
- **THEN** пользователь попадает на экран входа без ошибок в интерфейсе

#### Scenario: Вход и выход из браузера
- **WHEN** пользователь входит и затем выходит
- **THEN** оба запроса идут из браузера в BFF, cookie сессии ставится и снимается BFF

### Requirement: Адреса BFF во фронтенде
Фронтенд SHALL использовать два адреса BFF: внутренний `BFF_URL` для запросов сервера при отрисовке и публичный `BFF_PUBLIC_URL` для браузера (по умолчанию равен `BFF_URL`). Публичный адрес передаётся в страницу при серверной отрисовке, так что собранный клиентский пакет не зависит от окружения.

#### Scenario: Разные адреса
- **WHEN** заданы `BFF_URL=http://bff-crm:8080` и `BFF_PUBLIC_URL=http://localhost:8081`
- **THEN** сервер фронтенда обращается к первому адресу, а браузер — ко второму

#### Scenario: Публичный адрес не задан
- **WHEN** задан только `BFF_URL`
- **THEN** браузер использует тот же адрес
