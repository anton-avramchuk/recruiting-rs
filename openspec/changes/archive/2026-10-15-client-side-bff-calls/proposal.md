## Why

Сейчас каждое обращение браузера к данным идёт цепочкой браузер → web-crm (server function) → BFF → сервис. Лишний прыжок добавляет задержку, адреса вида `/api/list_vacancies12776126088031724206` нечитаемы в DevTools, а каждый запрос требует отдельной обёртки-функции с разбором ответа на сервере. BFF уже умеет принимать запросы прямо из браузера (cookie сессии `HttpOnly`, CSRF-заголовок, прокси `/api/*`), поэтому после первой отрисовки браузер может ходить в него сам.

## What Changes

- Браузер после гидратации отправляет все запросы за данными и мутации **напрямую в BFF** (по публичному адресу) с cookie сессии и заголовком `x-csrf-token`; server functions для данных, входа и выхода убираются.
- Первая отрисовка на сервере (SSR) по-прежнему содержит данные: сервер фронтенда запрашивает BFF по внутреннему адресу с cookie входящего запроса. Одна и та же функция доступа к данным работает и на сервере, и в браузере.
- Оба BFF получают настраиваемый CORS: разрешённые источники перечисляются явно (`CORS_ORIGINS`), ответы допускают cookie (credentials), предзапросы (preflight) отвечают без сессии и CSRF; без настройки поведение прежнее (CORS выключен). Подстановочный `*` запрещён.
- Фронтенды получают второй адрес BFF: `BFF_URL` (внутренний, для SSR) и `BFF_PUBLIC_URL` (адрес для браузера, по умолчанию равен `BFF_URL`), публичный адрес передаётся в страницу при отрисовке.
- Формы входа и редактирования, построенные на `ServerAction`/`ActionForm`, переводятся на обычные действия (`Action`) с клиентскими вызовами; прогрессивное улучшение без JavaScript для форм не сохраняется.
- Compose и e2e-стенд публикуют порты BFF и задают `CORS_ORIGINS` и `BFF_PUBLIC_URL`.

### Out of scope

- Генерация типизированного клиента из OpenAPI.
- Единый reverse proxy перед фронтендом и BFF (в проде удобно, но это инфраструктура, а не код приложения).
- Изменение моделей данных, маршрутов BFF и прав.

## Capabilities

### Modified Capabilities
- `bff-session`: CORS для обращений браузера напрямую.
- `web-shell`: доступ к данным из браузера, SSR с данными, адреса BFF.

## Impact

- `bff-core` (middleware CORS, конфиг), `bff-crm`, `bff-admin` (переменная `CORS_ORIGINS`).
- `ui-kit`: изоморфный клиент BFF (`api`), вход/сессия без server functions.
- `web-crm`, `web-admin`: все server functions данных заменены вызовами клиента; публичный адрес в оболочке страницы.
- `docker-compose.yml`, e2e-стенд, README.
- Ограничение развёртывания: браузер должен считать фронтенд и BFF одним «сайтом» (общий регистрируемый домен или `localhost`), иначе cookie `SameSite=Lax` не уйдёт с кросс-запросом; документируется.
