# Design

## Context

Скелет платформы (см. архив `bootstrap-rust-platform`) даёт форму сервиса (`domain / application / infrastructure / api`), RLS через `TenantTx`, EdDSA-токены identity, два BFF и Leptos-приложения. Референс домена — `Person` из .NET-версии (`recruiting-crm/Modules/Candidate`): агрегат со значимыми типами контактов, нормализованными ключами дедупликации и правилом `PersonMatcher` (email → телефон → ФИО). Правила разработки — TDD, DDD, общий код в общих crates (см. `openspec/config.yaml`).

Новое для платформы: первый сервис, который сам проверяет токены; первый BFF-маршрут не в identity; первые доменные таблицы под RLS.

## Goals / Non-Goals

**Goals:**
- Кандидат как агрегат с инвариантами в `domain`, без зависимостей от HTTP и БД.
- Перенести из .NET-версии смысл правил (нормализация, дедупликация, стаж по истории), а не форму кода.
- Показать, что скелетная форма сервиса работает для домена, и вынести всё, что понадобится второму сервису, в общие crates.

**Non-Goals:**
- Вакансии, отклики, заметки, импорт и разбор резюме, полнотекстовый поиск, сохранённые поиски, архивация.
- Ротация ключей по расписанию и отзыв токенов (проверка лишь переживает смену ключа).
- Кросс-сервисные события.

## Decisions

**Сервис `candidate`, БД `candidate`.** Один crate с модулями скелета. Таблицы `persons`, `employments`, `educations`, все с `tenant_id` и RLS; дочерние таблицы ссылаются на `persons` по `(tenant_id, person_id)` внешним ключом с `ON DELETE CASCADE`. Навыки — `text[]` в `persons` (список короткий, отдельной сущностью не является; фильтр по навыку идёт по массиву с GIN-индексом). Нормализованные ключи дедупликации (`normalized_name`, `normalized_email`, `normalized_phone`) хранятся рядом и пересчитываются доменом при каждой записи; по ним индексы `(tenant_id, …)`. Альтернатива «отдельная таблица навыков» отклонена: нет ни справочника, ни запросов, которым она нужна.

**Агрегат и значения.** `Person` владеет коллекциями мест работы и образования; замена списков — операции агрегата, инварианты (дата окончания не раньше начала) проверяются в домене. Значимые типы `Email`, `Phone`, `Telegram`, `WhatsApp`. `Email` уже есть в identity, `Phone` нужен второму сервису — поэтому `Email` и `Phone` переезжают в новый crate **`platform-values`** (identity переходит на него), а `Telegram`/`WhatsApp` остаются в домене candidate: они нужны только ему (правило «выносим со второго потребителя»). Пустой ввод означает «контакта нет», невалидный — ошибка домена → 400 с указанием поля.

**Стаж.** `ExperienceYears` не хранится как истина: считается функцией домена по объединению периодов работы (текущее место — до «сегодня», время подставляется параметром ради тестов). В БД хранится вычисленное значение `experience_years` — чтобы фильтровать по диапазону индексом, а не пересчётом; оно обновляется в той же транзакции при замене списка мест работы. Пока истории нет, берётся заявленный `declared_experience_years`. Альтернатива «считать на лету при каждом запросе списка» отклонена: фильтр по стажу стал бы сканом.

**Дедупликация.** `PersonMatcher` — чистая функция домена: на вход кандидаты-претенденты, выбранные запросом по трём ключам, на выход победитель и признак совпадения (`email`, `phone`, `name`). Создание: `POST /persons` ищет дубль; найден и нет `confirm_duplicate: true` → 409 `application/problem+json` с расширением `duplicate {id, full_name, matched_by}`. Решение «подтвердить» принимает клиент повторным запросом — без состояния на сервере. Совпадение только по ФИО — самый слабый признак, но не отбрасывается (в выгрузках контактов часто нет).

**API (internal к BFF).** `POST /persons`, `GET /persons`, `GET /persons/{id}`, `PATCH /persons/{id}`, `PUT /persons/{id}/employments`, `PUT /persons/{id}/educations`, `DELETE /persons/{id}`. Список: `q`, `source`, `skill`, `min_experience`, `max_experience`, `min_salary`, `max_salary`, `page`, `page_size` (по умолчанию 20, максимум 100). Поиск `q` — `ILIKE` с экранированием спецсимволов по ФИО, email, навыкам и по цифрам телефона (нормализованный телефон). Решение по `PATCH`: частичное обновление, поле «не передано» ≠ «очистить» (`null`/пустая строка очищает контакт). Права: `ReadData` для GET, `WriteData` для POST/PATCH/PUT, новое `DeleteData` (только `owner`) для DELETE; тенант берётся только из токена, запросы идут через `TenantTx`.

**Проверка токенов вне identity.** В `platform-auth` добавляется `TokenVerifier::remote(jwks_url, audience)`: ключ хранится за `RwLock`, начальная загрузка по JWKS identity выполняется лениво и с повтором (сервис стартует и без identity — тогда 401); при ошибке подписи ключ перечитывается не чаще раза в 30 секунд и проверка повторяется один раз. Расширение `AuthUser` остаётся прежним (через `FromRef<Arc<TokenVerifier>>`), поэтому identity и admin не меняются. Альтернативы: общий секрет (отклонён — HS256 ломает модель «подписывает один сервис»); вызов introspection в identity на каждый запрос (отклонён — сеть на горячем пути).

**Маршрутизация BFF в несколько бэкендов.** `BffConfig` получает именованные upstream-ы: `upstreams: HashMap<String, String>`, а `AllowRule` — имя upstream-а. Аутентификация (`login/refresh/logout`) остаётся у identity через `UpstreamAuth`. `bff-crm` объявляет `identity` и `candidate`; маршруты кандидатов — `/persons*` → `candidate`, `/users*` → `identity`. Для обратной совместимости `upstream_base_url` для одиночных BFF сохраняется как upstream по умолчанию, `bff-admin` не меняется. Ошибка соединения с одним upstream-ом → 502 только для его маршрутов.

**Frontend.** `web-crm`: маршруты `/candidates` (список), `/candidates/new`, `/candidates/:id` (карточка). Все обращения идут через server functions → `ui_kit::server::call` → `bff-crm` (как в скелете). Список — `Resource` от сигналов поиска/фильтров/страницы с debounce на стороне клиента; форма создания обрабатывает 409 как состояние «найден дубль» (баннер с ссылкой и кнопкой «Создать всё равно», которая повторяет запрос с подтверждением). Карточка: разделы «Контакты и профиль», «Опыт», «Образование» редактируются независимо (каждый — своя серверная функция). Удаление: двухшаговое подтверждение в интерфейсе. Права из токена (роли в превью сессии) скрывают кнопки; серверные проверки остаются источником истины.

**Общие DTO.** `candidate-contracts` (serde + utoipa, без `v4` у uuid ради wasm) — `PersonDto`, `PersonSummaryDto`, `CreatePersonRequest`, `UpdatePersonRequest`, `EmploymentDto`, `EducationDto`, `PersonPage`, `DuplicateInfo`. Используются сервисом и фронтендом, как `admin-contracts`.

**Тесты.** Домен — юнит-тесты (нормализация, матчер, стаж по объединению периодов, валидация); сервис — интеграционные на реальном PostgreSQL (RLS, дубль, поиск/фильтры/пагинация, права, изоляция между тенантами, `tables_without_rls`); верификатор JWKS — тест со сменой ключа; BFF — тесты маршрутизации с двумя мок-upstream-ами; e2e — API-сценарий и сценарий в браузере.

## Risks / Trade-offs

- [Удаление кандидата необратимо, а отклики (следующий change) будут на него ссылаться] → при появлении откликов удаление заменяется запретом или архивацией; в спеке удаление описано как необратимое для текущей версии.
- [Совпадение только по ФИО даёт ложные предупреждения о дубле] → это лишь предупреждение с явным «Создать всё равно»; признак совпадения показывается пользователю.
- [Хранимый `experience_years` может разойтись с историей] → обновляется в той же транзакции, что и список мест работы; тест на согласованность; текущее место растёт со временем — значение пересчитывается при записи, поэтому для «текущих» мест фильтр по стажу приблизителен до ближайшей правки (принято, пересчёт фоновой задачей — отдельный change).
- [Перечитывание JWKS может использоваться для нагрузки подделанными токенами] → ограничение частоты и один повтор на запрос.
- [BFF с несколькими upstream-ами усложняет конфигурацию] → явные именованные upstream-ы и тесты на каждый маршрут allowlist.

## Migration Plan

Новая БД `candidate` создаётся init-скриптом compose (роль `recruiting_app` получает права по умолчанию) и миграциями сервиса при старте; существующие данные не затрагиваются. Откат — остановить сервис `candidate` и убрать `CANDIDATE_URL` из `bff-crm`: маршруты кандидатов начнут отвечать 502, остальное работает. Миграция identity на `platform-values` не меняет схему и контракты.
