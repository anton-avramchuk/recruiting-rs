## Context

`AnalyticsService::report` собирает факты об откликах периода (`facts`), недельные счётчики, число повторных кандидатов и список вакансий, а чистые функции `domain::analytics` считают воронку, медианы и источники. У вакансии есть `client_id`, заказчики лежат в проекции `clients` (имя, архив). Метрики по источникам уже определяют «дошёл до интервью» как `effective_reached() >= 3`.

## Goals / Non-Goals

**Goals:** таблица заказчиков, фильтр `client_id`, выбор заказчика на экране.
**Non-Goals:** фильтр по нескольким заказчикам, сравнение периодов, отчёт по контактам, экспорт, показатели «выручки» и срок закрытия вакансии как метрика заказчика.

## Decisions

- **`AppFact.client_id: Option<Uuid>`**: факты запрашиваются с `v.client_id` (JOIN `vacancies`). Фильтр — условие в SQL (`$2::uuid IS NULL OR v.client_id = $2`) для `facts`, `week_counts`, `repeat_people` (для повторных кандидатов считаются отклики на вакансии этого заказчика) и в `vacancies::list(conn, client_id)` (параметр уже есть).
- **Чистая функция `domain::analytics::clients(facts: &[AppFact], vacancies: &[VacancyRef]) -> Vec<ClientStat>`**: группировка по `client_id` (`None` — «Без заказчика»); отклики, дошедшие до интервью (`effective_reached() >= 3`), вышедшие (`stage == Hired`), медиана через `days_to_hire` по группе; число вакансий и активных откликов берётся из списка вакансий (`VacancyRef { client_id, active_applications }`). Названия и признак архива подставляет сервис по проекции (`clients`), чтобы домен остался чистым. Сортировка: отклики по убыванию, название, «Без заказчика» последним при равенстве.
- **Таблица не сужается фильтром**: для неё факты и вакансии берутся без фильтра, поэтому сервис делает один запрос фактов без фильтра и затем фильтрует в памяти для остальных блоков (`facts.iter().filter(client)`); недельные счётчики и повторные кандидаты — отдельные запросы с фильтром. Так базовые данные читаются один раз.
- **Заказчик без вакансий не попадает в таблицу** (нет смысла показывать нули без вакансий); заказчик с вакансиями, но без откликов — попадает.
- **Валидация**: `client_id` разбирается как UUID; ошибка — `FunnelError::BadQuery` → 400 (как у `days`). Чужой или неизвестный заказчик не проверяется на существование: пустая выборка — естественный результат RLS и фильтра.
- **Контракты**: `ClientStatDto { client_id: Option<Uuid>, name, archived, vacancies, active_applications, applications, interviews, conversion, hired, median_days_to_hire: Option<f64> }`, `AnalyticsDto.clients: Vec<ClientStatDto>`. Поле добавляется с `#[serde(default)]` для обратной совместимости клиентов.
- **Интерфейс** (`apps/web-crm/src/analytics.rs`): `get_analytics(days, client_id: String)`; `RwSignal<String>` с выбранным заказчиком; `<select>` заполняется из `clients` последнего ответа без фильтра (хранится отдельным сигналом, чтобы список не пропадал при фильтре); таблица с кнопкой-строкой (клик ставит фильтр) и ссылкой `/clients/{id}`; строка «Без заказчика» без ссылки и без фильтра.
- **Кеширование/нагрузка**: аналитика считается на лету (как сейчас); один дополнительный JOIN по `vacancies` на запрос фактов.

## Risks / Trade-offs

- Фильтрация фактов в памяти при больших организациях: объём ограничен периодом (до 365 дней) и уже читается целиком сегодня — приемлемо.
- «Без заказчика» исчезнет, когда старым вакансиям назначат заказчиков; строка показывается только при наличии таких вакансий.
- Название заказчика берётся из проекции, которая догоняется при обращении к вакансиям; в аналитике сервис также вызывает догон заказчиков (`ClientsSync`), чтобы имена были актуальны.
