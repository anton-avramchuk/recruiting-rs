# Design

## Context

Сделано: платформа (identity, admin, два BFF, Leptos-приложения), сервис `candidate` с карточками, поиском и историей (см. архив `add-candidates`). Эталон поведения — прототип «Ритм» (`C:\screens\index.html`): модель `person` ↔ `app` (отклик) ↔ `vacancy`, 8 этапов, SLA, совпадение, групповые действия, панель человека, доска с перетаскиванием. В .NET-версии воронка живёт в отдельном сервисе `recruitment`; данные людей ей приходится получать из `candidate`. Правила проекта: TDD, DDD, общий код — в общие crates (`openspec/config.yaml`).

Главная сложность — данные двух сервисов в одном экране: таблица откликов фильтруется, ищется и сортируется по полям человека (имя, источник, город, зарплата), доска показывает имена на карточках, а воронка не должна падать вместе с `candidate`.

## Goals / Non-Goals

**Goals:**
- Отдельный контекст `recruitment` с агрегатами `Vacancy` и `Application` и инвариантами этапов в домене.
- Списки откликов одним SQL-запросом (фильтры, поиск, сортировка, пагинация, счётчики), без вызова соседнего сервиса на каждую строку.
- Воронка читается и пишется, пока `candidate` недоступен; изменения людей видны при следующем чтении.
- Интерфейс в стилистике «Ритм» без потери скорости: действие — один клик.

**Non-Goals:**
- Реальная почта, календарь и кадровые системы; импорт файлов; режим разбора; «Сегодня»; аналитика; палитра и горячие клавиши.
- Настраиваемые этапы и SLA, оценка человека, архивация вакансий.
- Общая шина событий (Redis pub/sub, outbox-воркеры).

## Decisions

**Сервис `recruitment`, БД `recruitment`.** Форма сервиса та же (`domain / application / infrastructure / api`). Таблицы (все с `tenant_id` и RLS): `vacancies`, `applications`, `application_events`, `interviews`, `people` (проекция), `people_sync` (курсор по организации). Составные внешние ключи `(tenant_id, …)` — как в `candidate`. Уникальность `(tenant_id, person_id, vacancy_id)` для откликов. Альтернатива «вакансии и отклики внутри candidate» отклонена: пользователь выбрал раздельные сервисы, а воронка и карточки человека развиваются разными темпами.

**Проекция людей и лента изменений (pull on read).** `candidate` пишет в таблицу `person_changes(seq, tenant_id, person_id, deleted, snapshot jsonb)` **в той же транзакции**, что и изменение человека; при записи старые строки того же человека удаляются, поэтому таблица не больше числа людей и отдаёт состояние, а не журнал. Миграция заполняет ленту текущими кандидатами. Внутренний эндпоинт `GET /internal/tenants/{tenant_id}/person-changes?after&limit` (сервисный токен, чтение через `TenantTx`) возвращает записи с `seq > after` по возрастанию. `recruitment` перед каждым чтением и перед созданием отклика синхронизирует **свою** организацию: читает ленту от сохранённого курсора страницами по 500, применяет их (upsert в `people`, для удалений — удаление проекции и откликов человека) и сдвигает курсор — всё в одной транзакции страницы. Конкурентные синхронизации одной организации исключены `pg_try_advisory_xact_lock`: проигравший пропускает синхронизацию и читает то, что есть. При ошибке сети синхронизация логируется и пропускается: список строится по проекции, то есть по последним известным данным. Это даёт read-your-writes (правка человека видна в воронке сразу после неё), не требует фоновых задач и не нарушает изоляцию: лента читается строго в контексте одной организации. Альтернативы: вызов `candidate` на каждую строку (отказ воронки при его падении, фильтры по полям человека невозможны), BFF-агрегация (бизнес-логика в BFF, сортировка и фильтры по чужим полям), событийная шина (новая инфраструктура и потеря событий).

**Этапы и правила — в домене.** `Stage` (8 значений, порядок, ключ) и функции `next`, `is_active`, `overdue(stage, elapsed)` лежат в `recruitment-contracts` (нужны и фронтенду для названий и порядка), а проверка переходов — в `domain` сервиса. Свободный перевод на любой этап; `next` — по порядку, недоступен из «Выход»/«Отказ». Просрочка вычисляется из `now() - stage_changed_at` (в SQL и в домене по одному правилу, покрыто тестом на согласованность). Время на этапе хранится как момент входа, а не как счётчик часов.

**Совпадение.** В проекции хранится `skills_lower text[]`, у вакансии — `required_skills_lower`. Процент считается в SQL как `round(100 * |пересечение| / |требуемые|)`, `NULL` без требований. Не хранится — следует за правками.

**История и имитации.** `application_events(kind, text, at, actor)`: `created`, `stage`, `rejected`, `letter`, `interview`, `handoff`. «Письмо», «приглашение» и «передача» — только запись события (флаг `simulated` в тексте не нужен: интерфейс и README говорят об имитации). `interviews(application_id, scheduled_at)` хранит назначенные интервью — основа для будущего экрана «Сегодня». Время события — серверное, источник «сейчас» подменяется в тестах (`Clock`, как в candidate).

**API.** `GET/POST /vacancies`, `GET/PATCH /vacancies/{id}`; `GET/POST /applications`, `GET /applications/{id}` (с историей и всеми откликами человека), `POST /applications/{id}/stage|next|reject|interviews|handoff`, `POST /applications/bulk`. Список откликов — один SQL с `LEFT JOIN people`, `EXISTS`-фильтрами, `count(*) OVER()` для итога и подзапросом числа откликов человека; поиск экранирует `LIKE` общим `platform_db::contains_pattern`. Права: `ReadData` для GET, `WriteData` для остальных. Все идентификаторы проверяются в контексте организации (404 для чужих).

**BFF.** `bff-crm` получает третий upstream `recruitment` (`RECRUITMENT_URL`) и правила `/vacancies*`, `/applications*`. Внутренние маршруты `candidate` для BFF закрыты.

**Фронтенд.**
- *Оформление.* `ui-kit` получает токены «Ритм» (бумага/поверхность/чернила, сигнал `#F2481B`, моноширинные подписи, плотные таблицы); цвет сигнала применяется только классами срочности. Бренд «Ритм», навигация «Вакансии / Отклики / Кандидаты» (+ «Интервью» остаётся заглушкой).
- *Данные.* Server functions `web-crm` вызывают BFF (как раньше); панель человека собирает карточку из `GET /api/persons/{id}` и `GET /api/applications/{id}`.
- *Доска.* HTML5 drag-and-drop на `dragstart/dragover/drop` Leptos-обработчиках; перенос выполняется оптимистично: карточка сразу в новой колонке, при отказе сервера возвращается. Перевод по кнопкам панели не зависит от drag-and-drop (доступность).
- *Таблица.* Фильтры и поиск с задержкой 250 мс (тот же `DebouncedInput`), выбор строк локальным состоянием, групповая панель.
- *Панель.* Правая выдвижная панель с собственным ресурсом; Esc закрывает. Состояние панели и доски синхронизируется через общий сигнал версии.

**Инфраструктура.** Новый процесс в compose, цель в Dockerfile, БД в `postgres-init.sql`, процесс в e2e-стенде, демо-данные (вакансии и отклики) в `seed-demo.sh`.

**Тесты.** Домен — юнит (этапы, `next`, SLA на границах, совпадение). Сервис — интеграция на реальном PostgreSQL (RLS, уникальность, история, фильтры/сортировка/пагинация, групповые действия). Синхронизация — против мок-`candidate` (изменение, удаление, недоступность, конкуренция). Сквозные — API-сценарий через BFF и браузерные сценарии (перетаскивание синтетическими `DragEvent`, таблица, панель).

## Risks / Trade-offs

- [Проекция может отстать, если candidate недоступен] → список помечен ответом `x-people-stale: true`, интерфейс показывает ненавязчивое предупреждение; при восстановлении догоняется автоматически.
- [Синхронизация на каждом чтении добавляет вызов] → при отсутствии изменений это один быстрый запрос по индексу `(tenant_id, seq)`; при необходимости добавляется короткий кэш «нет изменений» (не нужен для скелета).
- [Двойная запись в двух БД при создании кандидата с вакансией] → интерфейс создаёт кандидата, затем отклик; при сбое второго шага человек остаётся без отклика, а интерфейс говорит об этом и ведёт в карточку.
- [Удаление кандидата стирает отклики и историю воронки] → предупреждение в интерфейсе; архивация вместо удаления — отдельное решение позже.
- [Сортировка и поиск по `LIKE` без полнотекстового индекса] → достаточно для сотен тысяч строк с индексами по организации; полнотекстовый поиск — отдельный change.
- [Совпадение только по навыкам грубо] → показывается как подсказка; формула вынесена в одну функцию и легко заменяется.
- [Размер этого change велик] → разбит на независимо проверяемые задачи; каждая группа заканчивается зелёными тестами.

## Migration Plan

Миграции `candidate` аддитивны (новые столбцы с пустыми значениями, новая таблица ленты, заполняемая из существующих кандидатов). Новая БД `recruitment` создаётся init-скриптом compose и миграциями сервиса при старте. Откат: остановить `recruitment` и убрать `RECRUITMENT_URL` — маршруты воронки отвечают 502, кандидаты работают; лента `candidate` безвредна без потребителя.
