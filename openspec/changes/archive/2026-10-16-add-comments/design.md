## Context

Пользователь в токене представлен только `sub` (идентификатор) и ролями (`platform-auth::Claims`); имя хранится в identity (`display_name`). Сервисы повторяют один каркас: domain, application, infrastructure, api, миграции с RLS, тест-страж `tables_without_rls`, `TenantTx`. Фронтенд ходит в BFF напрямую (`ui_kit::api::call`). У человека уже есть одно поле «заметка» (`persons.note`, редактируется в панели и карточке).

## Goals / Non-Goals

**Goals:** одна модель комментариев для трёх видов объектов, авторство и права, общий компонент интерфейса, окружение.
**Non-Goals:** упоминания (@), вложения и форматирование, ответы-ветки, уведомления, поиск по комментариям, реакции, счётчики комментариев в списках, миграция существующего поля «заметка» в комментарии.

## Decisions

- **Отдельный сервис `comment`** (решение пользователя) с полиморфной привязкой: `target_type ∈ {client, vacancy, person}` + `target_id`. Контекст не знает об устройстве объектов и не проверяет их существование: комментарий к удалённому объекту недостижим из интерфейса (лента запрашивается по идентификатору существующего объекта). Осиротевшие записи допустимы; чистка — отдельным заданием позже.
- **Модель**: `comments(id, tenant_id, target_type, target_id, author_id, author_name, body, created_at, edited_at NULL)`; индекс `(tenant_id, target_type, target_id, created_at, id)`; RLS (FORCE), политика по `app.tenant_id`. Домен: `Comment` (создание с валидацией длины и типа, правка/удаление — правило «автор» и «owner» как чистые функции прав), `TargetType`.
- **Имя автора**: `Claims` получает `name: Option<String>` (`#[serde(default, skip_serializing_if = "Option::is_none")]`) — старые токены остаются валидными; identity подставляет `display_name`, а при пустом — email. Комментарий хранит снимок имени. Альтернативы (запрос к identity при чтении, клиентская подстановка) отвергнуты: лишняя связность и недоверенные данные.
- **API** (`/comments`): `GET /comments?target_type&target_id&after&limit` (по умолчанию 50, максимум 200; `after` — курсор по `(created_at, id)`; ответ `{items, next}`), `POST /comments`, `PATCH /comments/{id}` (только автор), `DELETE /comments/{id}` (автор или `owner`). Права: чтение — все роли, запись — `owner`/`recruiter`; ошибки 400/401/403/404 в `problem+json`, поле ошибки в `field`.
- **BFF**: allowlist `/comments` → `COMMENT_URL`; CORS и CSRF — как у остальных маршрутов; мок upstream в `bff-core::testing`.
- **Интерфейс**: компонент `Comments` (`apps/web-crm/src/comments/`: `mod`, `server`, `view`) принимает `target_type`, `target_id` и `can_write`/`user_id`/`is_owner` из сессии; список перезагружается после действий; добавление — `Action`; «изменено» по `edited_at`; ошибка загрузки — сообщение с повтором. Подключается на карточке заказчика (add-clients), в карточке вакансии (под фактами), в карточке кандидата и в панели человека (по `person_id`).
- **Окружение**: этап `comment` в Dockerfile, сервис в compose, БД `comment` в `postgres-init.sql`, `COMMENT_URL` у `bff-crm`, демо-сид с парой комментариев, `tests/e2e::Stack` поднимает сервис.
- **Порядок**: токен и identity → контракты и домен `comment` → БД и API → BFF → интерфейс → окружение; красные тесты первыми на каждом слое. Реализуется после `add-clients` (клиентские комментарии); остальные типы объектов работают независимо.

## Risks / Trade-offs

- Снимок имени устаревает при смене имени пользователя — для переписки это нормально и честнее, чем «задним числом».
- Осиротевшие комментарии после удаления кандидата/вакансии занимают место; риск мал, откладываем чистку.
- Права «автор» опираются на `sub` из токена: при пересоздании пользователя (новый идентификатор) старые комментарии перестанут быть «своими» — приемлемо.
- Ещё один сервис в e2e-стенде и compose увеличивает время запуска.
