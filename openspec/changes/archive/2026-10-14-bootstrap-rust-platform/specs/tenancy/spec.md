## ADDED Requirements

### Requirement: Определение тенанта запроса
Система SHALL определять тенанта каждого пользовательского запроса по аутентифицированной личности (claim токена), а не по параметру, подконтрольному клиенту. Запрос без определимого тенанта к тенантным ресурсам MUST быть отклонён.

#### Scenario: Тенант из токена
- **WHEN** аутентифицированный пользователь тенанта A обращается к тенантному ресурсу
- **THEN** запрос выполняется в контексте тенанта A

#### Scenario: Подмена тенанта клиентом
- **WHEN** пользователь тенанта A передаёт в запросе идентификатор тенанта B (заголовок, путь или тело)
- **THEN** идентификатор игнорируется или запрос отклоняется, данные тенанта B не возвращаются

### Requirement: Изоляция данных на уровне БД
Каждая тенантная таблица SHALL содержать `tenant_id` и быть защищена Row-Level Security так, что строки другого тенанта недоступны для чтения и записи, даже если прикладной запрос не содержит фильтра по тенанту.

#### Scenario: Запрос без фильтра
- **WHEN** в контексте тенанта A выполняется выборка всех строк тенантной таблицы без условия по `tenant_id`
- **THEN** возвращаются только строки тенанта A

#### Scenario: Запись в чужой тенант
- **WHEN** в контексте тенанта A выполняется вставка строки с `tenant_id` тенанта B
- **THEN** операция отклоняется базой данных

#### Scenario: Соединение без контекста
- **WHEN** тенантная таблица читается на соединении, где контекст тенанта не установлен
- **THEN** не возвращается ни одной строки

### Requirement: Сброс контекста при возврате соединения
Контекст тенанта MUST NOT переходить между запросами через пул соединений.

#### Scenario: Повторное использование соединения
- **WHEN** соединение, обслужившее тенанта A, переиспользуется для запроса тенанта B
- **THEN** запрос B видит только данные тенанта B
