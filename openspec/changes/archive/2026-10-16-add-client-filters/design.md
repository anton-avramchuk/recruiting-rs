## Context

`candidate` не знает о заказчиках: связь «человек — заказчик» существует только через отклики (`applications.person_id`, `applications.vacancy_id → vacancies.client_id`) в `recruitment`. Экран «Кандидаты» ходит в `GET /persons` (поиск, фильтры, страницы по 20). У `GET /vacancies` фильтр `client_id` уже есть (change `add-clients`), на экране «Вакансии» весь список грузится целиком и выбор вакансии хранится в `selected`.

## Goals / Non-Goals

**Goals:** фильтр кандидатов по заказчику без дублирования данных между сервисами; фильтр вакансий по заказчику на доске.
**Non-Goals:** проекция заказчиков в `candidate`; серверная композиция в BFF; фильтр по нескольким заказчикам; сортировка по заказчику.

## Decisions

- **Двухшаговый запрос из браузера** (выбранный вариант): шаг 1 — `GET /api/applications/people?client_id=…` → `{person_ids, truncated}`; шаг 2 — `GET /api/persons?ids=a,b,c&q=…&page=…`. Данные остаются в своих сервисах, BFF остаётся прокси. Путь `/applications/people` попадает под существующее правило allowlist `/applications` → `recruitment`.
- **`recruitment`**: `SELECT DISTINCT a.person_id FROM applications a JOIN vacancies v ON v.id = a.vacancy_id WHERE v.client_id = $1 ORDER BY a.person_id LIMIT 201` (201 — чтобы определить усечение); обязательный `client_id: Uuid` (отсутствует/мусор → 400 от `Query`). Идентификаторы людей в проекции совпадают с `candidate.persons.id`.
- **`candidate`**: `ListFilter.ids: Option<Vec<Uuid>>`; параметр `ids` — строка через запятую (`Option<String>`), разбор в `Uuid` с ошибкой 400 (`field: ids`), максимум 200; в SQL `AND id = ANY($n)`; пустая строка = нет фильтра. Для пустого списка людей заказчика клиент не вызывает `candidate` (показывает пустое состояние), потому что пустой `ids` по контракту означает «без ограничения».
- **Длина URL**: 200 UUID ≈ 7,4 КБ; ограничение 200 держит запрос в пределах типичных лимитов (8 КБ у axum/hyper по умолчанию без настройки — проверено в e2e с 200 идентификаторами); при превышении клиент показывает усечение.
- **Экран «Кандидаты»**: сигнал `client`; `Resource` по `(q, source, skill, min_experience, page, client)`: если `client` пуст — как сейчас; иначе сначала `people_of_client(client)`, затем `search_persons` с `ids`. Признак `truncated` показывается заметкой. Селектор заказчиков — тот же `list_clients("", true)`, что и на «Отклики».
- **Экран «Вакансии»**: сигнал `client`; `list_vacancies` принимает необязательный `client_id` (серверная функция/клиентская функция добавляет параметр); ресурс списка зависит от `client`; при смене заказчика `selected` сбрасывается на первую вакансию нового списка (существующий `Effect` уже выбирает первую, если текущей нет в списке); пустой список → пустое состояние. Палитра и другие потребители `list_vacancies()` вызывают без фильтра.
- **Права**: оба новых запроса — только чтение (`ReadData`).

## Risks / Trade-offs

- Два последовательных запроса добавляют задержку при включённом фильтре — приемлемо.
- Больше 200 людей у заказчика видны не все: пользователь уточняет поиском, а в крайних случаях пользуется экраном «Отклики» с пагинацией. Усечение явно показывается.
- `ids` в GET усложняет логи/кэш; альтернатива (POST-поиск) отвергнута ради единообразия API.
- Сортировка списка кандидатов остаётся по дате создания, не по откликам.
