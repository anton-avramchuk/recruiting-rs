## Context

Списки сейчас пишутся по месту: `candidate` и `recruitment` разбирают свои query-параметры и собирают SQL вручную (`LIST_FILTER`, `ListFilter`, `contains_pattern` из `platform-db`), `identity` отдаёт `GET /users` массивом целиком. В интерфейсе у каждого экрана свои сигналы фильтров, `DebouncedInput` и пейджер. Транзакции тенанта дают RLS (`TenantTx`). Ориентир — `cheetahrc`: `GridRequest`/`FilterDescriptor` (контракт), `GridModel` с белым списком столбцов (сервер), `Grid` + `GridSource` (интерфейс).

## Goals / Non-Goals

**Goals:** один формат запроса/ответа; безопасная сборка SQL без конкатенации клиентских значений; один компонент таблицы с серверной пагинацией, сортировкой, фильтрами столбцов и поиском; состояние в URL.
**Non-Goals:** виртуальная прокрутка и клиентский режим (все записи в браузере); макрос `derive` для схем (схемы задаются константами); перевод остальных списков; сохранение пользовательских представлений (набор фильтров, ширины столбцов); экспорт.

## Decisions

- **Три слоя, как в образце, но без макросов.** `grid-contracts` (serde, без sqlx/leptos; компилируется и для wasm), `platform-grid` (sqlx; зависит от контрактов и `platform-db`), `Grid` в `ui-kit` (зависит от контрактов). Схема грида — константа `GridSchema { source, key, columns: &[GridColumn] }`; `GridColumn { name, sql, ty, sortable, filterable }`, `ty` ∈ `Text`, `Int`, `Bool`, `Uuid`, `Timestamp`, `Date`. SQL-выражения берутся только из кода сервиса.
- **Контракт.** `GridQuery { page (с 1), page_size, sort: Vec<SortKey{field, desc}>, filter: Option<Filter> }`; `Filter` — либо группа `{logic: and|or, filters}`, либо условие `{field, operator, value, ignore_case}`; `GridPage<T> { items, total, page, page_size }`. В контракте же — разбор и сборка query-строки: `page`, `page_size`, `sort=email:asc,created_at:desc`, `filter=<JSON>` (одна JSON-строка вместо индексных ключей Kendo: короче и проще валидируется). Имена полей сопоставляются без учёта регистра и `_`.
- **Лимиты** (на сервере, ошибка 400 с `field`): размер страницы по умолчанию 20, максимум 100 (схема может уменьшить), глубина фильтра ≤ 4, условий ≤ 32, сортировка ≤ 3 ключей, длина значения ≤ 200 символов, `filter` в URL ≤ 4 КБ.
- **Сборка SQL.** `build(schema, &query) -> Result<Built, GridError>` отдаёт `where_sql`, `order_sql`, список параметров `Vec<Bind>` (`Text(String)`, `Int(i64)`, `Bool`, `Uuid`, `Timestamp`, `Date`) и `limit/offset`; значения приводятся к типу столбца при разборе (ошибка типа — 400), в SQL подставляются как `$n::тип`. Операторы строк: `contains/startswith/endswith` — `ILIKE $n ESCAPE '\'` с экранированием (`contains_pattern`), `eq/neq` с `ignore_case` — `lower(col) = lower($n)`; числа/даты — `= <> > >= < <=`; `isnull/isnotnull`; `isempty/isnotempty` (только Text). Оператор, не подходящий типу, — 400. К `ORDER BY` всегда добавляется ключ (`schema.key`) для стабильных страниц. Исполнение: `fetch_page(conn, schema, query, row_mapper)` — два запроса в одной транзакции тенанта (`SELECT count(*)` с тем же `WHERE` и страница); принадлежность тенанту обеспечивает RLS, а не `WHERE`.
- **Идентификация ошибок.** `GridError { field, message }` → 400 `ProblemDetails` с `field` (`filter`, `sort`, `page_size`, имя поля), так что интерфейс показывает понятное сообщение.
- **Пользователи в identity.** Схема над таблицей `users`: `id` (Uuid), `email`, `display_name`, `status` (Text, `eq`), `role` (Text, `array_to_string(roles, ',')` — фильтр `contains`), `created_at` (Timestamp); сортируются все, кроме `role`. `GET /users` принимает параметры грида и возвращает `GridPage<UserDto>`; сортировка по умолчанию — `email`. Старый ответ-массив убирается (потребитель один — `web-crm`). `GET /users/{id}` отдаёт одного пользователя (страница пользователя перестаёт искать его в общем списке).
- **Компонент `Grid`.** Параметры: `columns: Vec<Column<T>>` (`field`, `header`, `cell: fn(&T) -> AnyView`, `sortable`, `filter: ColumnFilter::{None, Text, Select(Vec<(value,label)>)}`, `searchable`), `load: Callback<GridQuery, Future<Result<GridPage<T>>>>`, `row_href: Option<fn(&T) -> String>`, `page_sizes`, `empty` (заголовок и подсказка), `toolbar` (слот). Внутри: состояние `GridState` (страница, размер, сортировка, фильтры столбцов, поиск) → `GridQuery` (общий поиск превращается в `or` по столбцам `searchable` с `contains`; фильтры столбцов — `and`); `Resource` по запросу внутри `Transition` (предыдущие строки остаются видимыми при загрузке); пейджер «1–20 из 135» с кнопками «Назад/Вперёд», выбор размера страницы; сортировка по клику на заголовок (asc → desc → без сортировки); текстовые фильтры с задержкой 300 мс (в `ui-kit` появляется общий `DebouncedText`; прежние `DebouncedInput` в экранах кандидатов, заказчиков и откликов остаются до их перевода на грид); сброс всех фильтров.
- **Состояние в URL.** `page`, `page_size`, `sort`, `q` (поиск) и `f.<поле>` (фильтры столбцов) читаются из `use_query_map` и записываются через `navigate` с `replace` — ссылку можно сохранить; смена фильтра или поиска возвращает страницу к 1.
- **Доступность и тестируемость.** Таблица — `<table>` с `<th scope=col aria-sort>`, у элементов `data-testid` (`grid`, `grid-row`, `grid-search`, `grid-page-info`, `grid-prev`, `grid-next`, `grid-filter-<поле>`, `grid-sort-<поле>`).
- **Транспорт из интерфейса.** Серверная функция принимает `GridQuery`, собирает query-строку из контрактов и вызывает `ui_kit::api::call(Method::Get, "/api/users?...")`; BFF пропускает query без изменений.

## Risks / Trade-offs

- Динамический SQL не кэшируется как prepared statement; для списков такого размера приемлемо.
- JSON в query-строке слегка некрасив, зато однозначен и ограничен по длине; запасной вариант — `POST /…/search`, если фильтры вырастут.
- `Grid` на первом применении (одна таблица) может оказаться неудобным для сложных списков (карточки, группировки); поэтому остальные экраны переводятся по одному, а API компонента фиксируется после второго применения.
- Ломающее изменение `GET /users` затрагивает тесты `identity` и страницу пользователя — обновляются в этом же change.
- Фильтр по роли — подстрока по строке `owner,recruiter`: корректен, пока названия ролей не вложены друг в друга; для собственных ролей (`add-custom-roles`) фильтр заменится на фильтр по `role_id`.
