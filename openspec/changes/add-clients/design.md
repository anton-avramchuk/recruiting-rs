## Context

Сервисы платформы устроены одинаково: `domain` (агрегаты, без ввода-вывода), `application` (сценарии, транзакции `TenantTx`), `infrastructure` (sqlx), `api` (axum + utoipa), миграции с RLS и тестом-стражем `tables_without_rls`. Данные между контекстами не делятся: `recruitment` получает людей из `candidate` по ленте `person_changes` (триггер БД в транзакции изменения, advisory-блокировка на организацию, курсор `people_sync`, догон при чтении, заголовок `x-people-stale`). Вакансия в `recruitment` сейчас хранит текстовые `department` и `hiring_manager`.

## Goals / Non-Goals

**Goals:** отдельный контекст «Заказчики» (DDD), привязка вакансии к заказчику и контакту, справочник должностей, раздел в интерфейсе, окружение (Docker, e2e, демо).
**Non-Goals:** портал заказчика и вход контактов в систему, письма и рассылки контактам, договоры и оплата, привязка заказчика к кандидату или отклику напрямую, удаление заказчиков, отчёты по заказчикам в «Аналитике» (отдельный change).

## Decisions

- **Отдельный сервис `client`** — решение пользователя; граница по DDD: заказчик и его контакты — один агрегат (`Client` владеет `Contact`; контакт не существует без заказчика, правило «контакт принадлежит заказчику» проверяется в агрегате), `Position` — отдельный агрегат-справочник. `recruitment` не обращается к БД `client` и не знает его модель: он хранит только идентификаторы и проекцию для показа.
- **Модель БД `client`**: `clients(id, tenant_id, name, name_key, note, archived, created_at, updated_at, UNIQUE(tenant_id, name_key))`; `positions(id, tenant_id, name, name_key, UNIQUE(tenant_id, name_key))`; `contacts(id, tenant_id, client_id, full_name, position_id NULL, email, phone, note, ...)` с составным внешним ключом `(tenant_id, client_id)` и `(tenant_id, position_id)` — ссылки не пересекают организации даже при ошибке кода; `client_changes(seq, tenant_id, entity, entity_id, deleted, snapshot)`. `name_key` = `lower(trim(name))` для уникальности. RLS на всех таблицах, роль приложения без BYPASSRLS.
- **Лента изменений** — по образцу `person_changes`: триггеры на `clients` и `contacts` (INSERT/UPDATE/DELETE) пишут в `client_changes` под advisory-блокировкой организации; триггер на `positions` при UPDATE названия переписывает записи ленты всех контактов этой должности (snapshot контакта содержит название должности). `GET /internal/tenants/{id}/client-changes?after&limit` под сервисным токеном (`ServiceCaller`), контракты — в новом crate `client-contracts` (DTO API, `ClientChange`, `ClientChangesPage`).
- **Проекция в `recruitment`** (миграция `0003`): `clients(tenant_id, client_id, name, archived)`, `client_contacts(tenant_id, contact_id, client_id, full_name, position)`, `clients_sync(tenant_id, position)` с RLS. `ClientFeed` (порт) + `HttpClientFeed`, `ClientsSync` по образцу `PeopleSync` (try-lock, постраничный догон, не падать при недоступности источника). Общий каркас догона (блокировка, цикл по страницам) выделяется без смены поведения, если это упрощает код; иначе допустима параллельная реализация.
- **Вакансия**: столбцы `client_id uuid NULL`, `contact_id uuid NULL` (без внешних ключей между сервисами; `contact_id` дополнительно проверяется по проекции на принадлежность заказчику). Столбцы `department` и `hiring_manager` остаются в БД без чтения/записи через API — данные не теряются. Домен `Vacancy` получает `ClientRef`; правила: при создании `client_id` обязателен, при правке нельзя очистить, смена заказчика сбрасывает контакт, если не передан новый. Проверка существования/архива/принадлежности делается в `VacancyService` после догона проекции: `unknown client` → 400 `client_id`, чужой контакт → 400 `contact_id`; если источник недоступен и заказчика нет в проекции — 503-подобная ошибка домена «заказчик пока недоступен» (400 с понятным текстом не годится, это не ошибка ввода → 503 `problem+json`).
- **API recruitment**: `CreateVacancyRequest`/`UpdateVacancyRequest` теряют `department`, `hiring_manager`, получают `client_id`, `contact_id`; `VacancyDto` — `client: {id, name, archived}?`, `contact: {id, full_name, position}?` (контакт удалён → `contact: null`, но `contact_id` в БД остаётся до правки). Список: фильтр `client_id`. Зависимые места: `ApplicationDetail` (`hiring_manager` → контакт), «Сегодня» (подпись вакансии: заказчик · город), палитра (мета вакансии: заказчик).
- **BFF**: allowlist `/clients`, `/contacts`, `/positions` → `CLIENT_URL` (новый апстрим в `CrmConfig`); мок апстрима в `bff-core::testing` получает эти маршруты.
- **Интерфейс**: новый модуль `apps/web-crm/src/clients/` (`mod`, `server`, `list`, `card`, `positions`); маршруты `/clients`, `/clients/:id`, `/clients/positions`; пункт навигации «Заказчики» (после «Вакансии»), команда палитры «Заказчики». Форма вакансии: `<select>` заказчика (активные) и контакта (по выбранному заказчику, перезагружается при смене). Клиентские вызовы — через `ui_kit::api::call` напрямую в BFF, как в остальных экранах.
- **Окружение**: целевой этап `client` в `docker/Dockerfile`; сервис `client` в compose (БД `client`, `SERVICE_TOKEN`, `IDENTITY_JWKS_URL`), `recruitment` и `bff-crm` получают `CLIENT_URL`; `postgres-init.sql` создаёт БД `client`; README описывает ручное создание БД на старом томе; демо-сид заводит заказчиков, должности, контакты и привязывает вакансии; `tests/e2e::Stack` поднимает сервис и пробрасывает URL.
- **Миграция данных**: старые вакансии остаются с `client_id = NULL`; интерфейс показывает «—» и позволяет назначить заказчика правкой. Автоматического создания заказчиков из `department` нет (текст неструктурирован).
- **Порядок работ**: контракты → домен и БД `client` → API/лента → проекция и вакансия в `recruitment` → BFF → интерфейс → окружение; сначала красные тесты на каждом слое.

## Risks / Trade-offs

- **Eventual consistency**: новый заказчик виден вакансиям после догона проекции (при следующем обращении к вакансиям; задержка — один запрос). Принимаем как у людей.
- **Удалённый контакт** остаётся в `vacancies.contact_id` как «висячая» ссылка; UI показывает «контакт удалён». Альтернатива (запрет удаления контакта, привязанного к вакансии) невозможна без синхронного вызова между сервисами.
- **Дублирование каркаса синхронизации** между людьми и заказчиками — приемлемо, пока источников два; при третьем выделить общий компонент.
- **BREAKING API вакансий**: `department` и `hiring_manager` исчезают из запросов и ответов; внешних потребителей, кроме `web-crm` и демо-сида, нет — обновляются в этом же change.
- Новый сервис увеличивает время сборки образов и e2e-стенда (ещё один процесс и БД).
