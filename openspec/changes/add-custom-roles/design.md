## Context

Роль — перечисление `Role` (`owner`, `recruiter`, `viewer`, `platform_admin`) в `platform-auth`; права выводятся из роли (`Role::permissions`), токен несёт `roles`, сервисы проверяют `claims.has(permission)` / `AuthUser::require`. В `identity` пользователь хранит `roles text[]` (не пустой, только роли тенанта). Фронтенд решает «можно ли писать/удалять» сравнением названий ролей в сессии (`can_write`, `can_delete`); комментарии разрешают владельцу удалять чужие по `Role::Owner`. BFF отдаёт интерфейсу `roles` из payload токена.

## Goals / Non-Goals

**Goals:** полный CRUD собственных ролей организации; назначение пользователю; права собственной роли работают во всех сервисах без знания о самих ролях.
**Non-Goals:** права по разделам (кандидаты/вакансии/аналитика отдельно); несколько ролей у пользователя; наследование ролей; право управления пользователями и ролями у собственных ролей; изменение встроенных ролей; немедленный отзыв access-токена.

## Decisions

- **Права собственной роли — подмножество `ReadData`, `WriteData`, `DeleteData`**; `WriteData` и `DeleteData` требуют `ReadData` (иначе 400). `ManageUsers` только у встроенного `owner`: собственная роль не может выдавать владельца и управлять ролями.
- **Хранение**: таблица `roles` в `identity` (`id`, `tenant_id`, `name`, `name_key` (нижний регистр для уникальности), `permissions text[]`, `created_at`), RLS как у `users`, `UNIQUE (tenant_id, name_key)`. Колонка `users.role_id uuid NULL REFERENCES roles(id)` без каскада. Инвариант пользователя: ровно одно из «встроенные роли непусты» или `role_id` задан; встроенный `roles` у пользователя с собственной ролью — пустой массив. Старое ограничение «хотя бы одна роль» переносится в домен как «встроенная роль или собственная роль».
- **Домен**: агрегат `CustomRole { id, tenant, name, permissions }` с проверками названия (не пусто, до 60 символов, не совпадает с названиями встроенных ролей без учёта регистра) и набора прав. `User` получает `role_id: Option<Uuid>`; смена роли заменяет одно на другое. Инвариант последнего владельца работает как раньше (учитывает только встроенный `owner`).
- **API**: `GET /roles` (встроенные + собственные, у каждой `kind: builtin|custom`, `permissions`, `users` — число пользователей), `POST /roles`, `PATCH /roles/{id}` (название, права), `DELETE /roles/{id}`; всё только для `ManageUsers` (владелец). `PATCH /users/{id}` и `POST /users` принимают `role_id` собственной роли вместо `roles` (взаимоисключающие, иначе 400); чужая/несуществующая роль → 400/404; ответ пользователя содержит `role_id` и `role_name`.
- **Удаление**: если роль назначена — 409 с числом пользователей; иначе 204.
- **Токен**: `Claims` получает `perms: Vec<Permission>` (`#[serde(default, skip_serializing_if = "Vec::is_empty")]`); `Claims::has` = права встроенных ролей ∪ `perms`. Права собственной роли берутся при выпуске токена (вход и refresh). `Permission` получает сериализацию в строки (`read_data`, `write_data`, `delete_data`). Старые токены остаются валидными.
- **Отзыв**: смена прав или названия-независимые изменения роли отзывают refresh-токены всех назначенных пользователей (как смена роли пользователя в `add-user-management`); переименование не отзывает.
- **BFF**: `user_preview` добавляет `perms` из payload; `/roles` добавляется в allowlist `bff-crm` (по умолчанию уходит в `identity`).
- **Фронтенд**: `UserInfo.perms`; `can_write` = есть `write_data`, `can_delete` = есть `delete_data`; для встроенных ролей права выводятся на клиенте по названиям (владелец, рекрутёр) как и раньше, для токена с `perms` — из них. Раздел «Безопасность» по-прежнему доступен только встроенному `owner`. Блок «Роли» на экране: таблица (название, тип, права, число пользователей), форма создания (название + три флажка), правка прав флажками и названия, удаление с подтверждением ошибки 409.
- **Комментарии**: проверка «удалить любой комментарий» меняется с `Role::Owner` на `claims.has(DeleteData)` — совпадает с поведением для встроенных ролей (право удаления только у владельца) и распространяется на собственные роли с этим правом.

## Risks / Trade-offs

- Собственная роль с `DeleteData` может удалять данные организации и чужие комментарии — это ожидаемо, владелец выдаёт её осознанно.
- Права в токене живут до истечения access-токена; при понижении прав действует прежнее окно, refresh отзывается.
- Пользователь со встроенными ролями и пользователь с собственной — две ветки в домене и UI; альтернатива (все роли в одной таблице) потребовала бы миграции встроенных ролей и отвергнута ради совместимости токенов.
- Расхождение названий ролей и прав на клиенте для встроенных ролей остаётся, пока токен не содержит полного набора прав (можно упростить позже).
