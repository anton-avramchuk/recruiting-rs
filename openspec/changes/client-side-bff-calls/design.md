## Context

Фронтенды (`web-crm`, `web-admin`) строят доступ к данным на server functions Leptos: браузер вызывает функцию сервера фронтенда, та через `ui_kit::server::call` ходит в BFF, пробрасывая cookie и запрашивая CSRF-токен. BFF уже умеет принимать запросы напрямую: сессия в cookie `HttpOnly; SameSite=Lax`, проверка `x-csrf-token` для изменяющих запросов, прокси `/api/*` по allowlist. Выбрано: браузер ходит в BFF напрямую (с CORS), а SSR сохраняет данные в первой отрисовке.

## Goals / Non-Goals

**Goals:**
- Одна функция доступа к данным, работающая на сервере (SSR) и в браузере.
- Безопасный CORS: явный список источников, credentials, CSRF не ослаблен.
- Публичный адрес BFF задаётся окружением, а не вшивается в wasm.

**Non-Goals:**
- Типизированный клиент из OpenAPI, единый reverse proxy, изменения API и прав.
- Работа форм без JavaScript.

## Decisions

**Изоморфный клиент `ui_kit::api::call(method, path, body) -> BffReply`.** Один асинхронный вызов с двумя реализациями за `cfg`:
- *ssr*: существующая логика `ui_kit::server::call` (cookie из входящего запроса через `leptos_axum::extract`, `Set-Cookie` из ответа обратно браузеру, CSRF-токен запрашивается у BFF);
- *hydrate*: `reqwest` в wasm (fetch) с `fetch_credentials_include()`, базовый адрес берётся из публичного адреса, для изменяющих запросов CSRF-токен получается `GET /bff/session` и кэшируется на время страницы (сбрасывается при 403 «csrf» и при входе/выходе).

Страницы и компоненты вызывают `api::call` из обычных `async` функций (`list_vacancies`, `application_action` и т. д.), которые используются в `Resource::new` (выполняются на сервере при SSR и в браузере при смене ключа) и в `Action::new` для мутаций. Альтернатива «два набора функций: server fn для SSR и fetch для клиента» отклонена: дублирование и риск расхождения. Альтернатива `gloo-net`: тянет второй HTTP-клиент; `reqwest` уже в проекте и поддерживает wasm.

**Публичный адрес.** Сервер фронтенда кладёт в контекст оба адреса (`BffUrl` внутренний, `BffPublicUrl`), а оболочка документа добавляет `<meta name="bff-url" content="…">`; клиентская реализация читает адрес из DOM при первом вызове. Так wasm-пакет одинаков для всех окружений. По умолчанию публичный адрес равен внутреннему.

**Cookie.** BFF сам ставит cookie сессии при `POST /bff/login` из браузера. Cookie привязана к хосту, а не к порту, поэтому cookie, поставленная BFF на `localhost:8081`, приходит и на `localhost:3000`: SSR фронтенда получает сессию и может подгрузить данные при первой отрисовке. Условие: фронтенд и BFF — один «сайт» (одинаковый регистрируемый домен или `localhost`); с `SameSite=Lax` кросс-сайтовые fetch не получат cookie. Требование зафиксировано в README; на другом домене понадобится общий родительский домен или reverse proxy.

**CORS в `bff-core`.** Слой (middleware) вокруг роутера:
- источники берутся из `BffConfig.cors_origins: Vec<String>` (из `CORS_ORIGINS`, список через запятую, пробелы обрезаются, `*` и пустые элементы отклоняются при запуске);
- для `OPTIONS` с разрешённым `Origin` слой отвечает 204 сам (до проверки сессии и CSRF) с `Allow-Methods`, `Allow-Headers: content-type, x-csrf-token`, `Allow-Credentials`, `Max-Age`;
- для остальных запросов с разрешённым `Origin` добавляет `Allow-Origin` (ровно этот источник), `Allow-Credentials: true`, `Vary: Origin`; `Expose-Headers` не требуется;
- источники вне списка и запросы без `Origin` проходят без изменений.

CSRF не ослабляется: изменяющий запрос с кастомным заголовком в любом случае требует предзапроса, а сам заголовок проверяется как раньше. Альтернатива `tower-http` CorsLayer: допустима, но нужна точная проверка источника по списку и ответ на предзапрос до слоя авторизации; собственный небольшой слой проще тестировать на нужных сценариях и не добавляет зависимость.

**Вход и сессия.** `get_session`, `login`, `logout` становятся клиентскими функциями `api::*`. `SessionCtx` загружает сессию через `Resource` (на сервере — с cookie запроса, в браузере — fetch). После входа/выхода кэш CSRF сбрасывается. Ответ 401 на клиентский запрос приводит к перенаправлению на `/login` (в `api::call` для hydrate), чтобы страницы не показывали ошибок «недоступно» при истёкшей сессии.

**Формы.** `ServerAction`/`ActionForm` заменяются на `Action` и обработчики `on:submit` с `prevent_default`. Поведение для пользователя прежнее (ошибки у полей, подтверждение дубля, состояние «Создаём…»), но без отправки формы при выключенном JavaScript. Классификаторы ответов (`classify_*`, `Reply`) остаются чистыми функциями и работают с телом ответа в обеих реализациях.

**Конфигурация и развёртывание.** `web-crm`: `BFF_URL`, `BFF_PUBLIC_URL`; `bff-crm`, `bff-admin`: `CORS_ORIGINS`. Compose публикует порты BFF (например, 8081 и 8082) и задаёт `CORS_ORIGINS=http://localhost:3000` / `http://localhost:3010`. e2e-стенд задаёт те же значения на свободных портах.

## Risks / Trade-offs

- [Cookie не уходит при кросс-сайтовых запросах] → документируем условие одного «сайта»; в прод-развёртывании предпочтителен общий домен либо reverse proxy, при котором CORS не нужен вовсе (поддерживается: пустой `CORS_ORIGINS` и `BFF_PUBLIC_URL` на том же origin).
- [Открытие BFF наружу расширяет поверхность атаки] → allowlist маршрутов, CSRF и HttpOnly-cookie уже защищают; CORS ограничен списком источников без `*`.
- [Потеря SSR-данных при ошибках] → при недоступности BFF во время SSR страница отдаёт состояние «Загрузка…», а клиент повторяет запрос после гидратации.
- [Формы без JS не работают] → принято: продукт — приложение с интерактивным интерфейсом.
- [Расхождение серверной и клиентской реализации `api::call`] → общий разбор ответа и единые тесты на чистые части (сборка URL, выбор заголовков), поведение в браузере покрыто e2e.

## Migration Plan

1. BFF получает CORS (выключен по умолчанию — безопасно выкатывать первым).
2. Фронтенды получают `BFF_PUBLIC_URL` и клиентский `api`, функции переносятся по разделам; на время переноса server functions и клиентские вызовы могут сосуществовать.
3. Compose и e2e переходят на раздельные адреса; удаляются неиспользуемые server functions и `ui_kit::server`-обёртки для данных.
Откат: вернуть предыдущий образ фронтенда (BFF с CORS ему не мешает).
