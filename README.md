# recruiting-rs

Мультитенантная рекрутинговая CRM целиком на Rust, включая фронтенд (Leptos). Платформа: организации (тенанты),
пользователи, вход, админка платформы, оболочка приложения («Ритм»), **кандидаты** (карточка с
контактами и историей, поиск и фильтры, предупреждение о дубле) и **воронка найма**: вакансии, отклики,
доска по этапам с перетаскиванием, таблица откликов с групповыми действиями и панель человека, а также
страница «Сегодня» (сводка, очередь, интервью дня, просрочка) и режим разбора новых откликов с клавиатуры
(T — открыть; ← отказ с письмом, → в скрининг, ↓ отложить, Esc — выйти), а также импорт кандидатов из CSV/XLSX и
PDF-резюме (Кандидаты → «Импорт») и «Аналитика» (воронка по пройденным этапам, сроки, источники, динамика, нагрузка
на вакансии). Палитра команд добавляется отдельным изменением.

## Архитектура

```
браузер ──► web-crm ──► bff-crm ──► identity ──┐
                              ├──► candidate (токены проверяет по JWKS identity)
                              ├──► client (заказчики, контакты, должности)
                              ├──► comment (комментарии к заказчикам, вакансиям, кандидатам)
                              └──► recruitment ──► candidate (лента изменений людей)
                                               └──► client (лента изменений заказчиков)
браузер ──► web-admin ► bff-admin ► admin ◄────┘ (справочник тенантов, создание владельца)
```

| Компонент | Назначение |
|---|---|
| `services/identity` | пользователи тенантов, вход, JWT (EdDSA), refresh с ротацией, роли; БД `identity` |
| `services/candidate` | кандидаты организации: контакты, места работы, образование, стаж, поиск, предупреждение о дубле; БД `candidate` |
| `services/recruitment` | вакансии, отклики и воронка (8 этапов, SLA, совпадение по навыкам, история, групповые действия); БД `recruitment`; людей берёт из `candidate`, заказчиков и контакты — из `client` (см. ниже); вакансия привязана к заказчику |
| `services/client` | заказчики организации, их контактные лица и справочник должностей (заказчик и контакты — один агрегат; архивация вместо удаления); БД `client`; лента изменений для `recruitment` |
| `services/comment` | комментарии к заказчикам, вакансиям и кандидатам (текст, автор и время; автор правит и удаляет свои, владелец удаляет любые); БД `comment`; имя автора берёт из токена |
| `services/admin` | реестр тенантов, платформенные администраторы, жизненный цикл тенанта; БД `admin` |
| `services/bff-crm`, `services/bff-admin` | по BFF на каждый фронтенд: серверная сессия в Redis, cookie `HttpOnly`, CSRF, прозрачный refresh, прокси по allowlist |
| `apps/web-crm`, `apps/web-admin` | Leptos (SSR + hydrate); каждое приложение общается только со своим BFF |
| `crates/platform-core` | конфиг из env, ошибки `problem+json`, health, shutdown, `TenantId` |
| `crates/platform-db` | пул, миграции, `TenantTx` (контекст тенанта для RLS), помощники тестов |
| `crates/platform-auth` | JWT, JWKS (в том числе удалённый верификатор), роли и права, extractor, межсервисный токен, пароли (argon2) |
| `crates/platform-values` | значимые типы `Email` и `Phone` с нормализацией |
| `crates/bff-core` | общий код обоих BFF |
| `crates/ui-kit` | общие Leptos-компоненты и server functions входа/сессии |
| `crates/admin-contracts`, `crates/candidate-contracts`, `crates/client-contracts`, `crates/comment-contracts`, `crates/recruitment-contracts` | DTO сервисов, общие для сервера и фронтенда (собираются и в wasm) |
| `tests/e2e` | запуск платформы процессами и сквозные тесты, в том числе в браузере |

Изоляция тенантов: общая БД сервиса, колонка `tenant_id` и Row-Level Security. Правила для новых
таблиц — в [docs/tenancy.md](docs/tenancy.md). Проектные решения и спецификации — в `openspec/`.

Правила разработки: TDD (сначала падающий тест), DDD (инварианты в `domain` без зависимостей от HTTP и БД),
общий код — в общие crates.

## Требования

- Rust (стабильный, см. `rust-toolchain.toml`) и цель `wasm32-unknown-unknown`:
  `rustup target add wasm32-unknown-unknown`
- Docker (PostgreSQL 17 и Redis)
- `cargo install cargo-leptos --locked` — сборка веб-приложений
- Google Chrome — для браузерных e2e-тестов
- по желанию `just` — короткие команды из `justfile`

## Быстрый старт

```sh
docker compose up -d --wait        # PostgreSQL (БД identity, admin, candidate, recruitment, client, comment; роль recruiting_app) и Redis
cargo run -p e2e --example dev     # вся платформа на свободных портах, одноразовые данные
```

Команда соберёт сервисы и веб-приложения, поднимет их, создаст демо-организацию и напечатает адреса
и учётные данные:

- клиентское приложение: организация `demo`, `owner@demo.io` / `demo-password-1` (с тремя демо-кандидатами, двумя вакансиями и откликами)
- админка платформы: `root@platform.io` / `root-password-1`

## В Docker

Вся платформа целиком, с демо-данными:

```sh
docker compose --profile app up -d --build   # первая сборка - несколько минут
```

- клиентское приложение: <http://localhost:3000>, организация `demo`, `owner@demo.io` / `demo-password-1`
- админка платформы: <http://localhost:3010>, `root@platform.io` / `root-password-1`
- PostgreSQL `localhost:5432`, Redis `localhost:6379`

Одноразовый контейнер `demo-seed` создаёт организацию `demo` и трёх кандидатов, двух вакансий и четырёх откликов (повторный запуск безопасен:
`docker compose --profile app run --rm demo-seed`). Остановить: `docker compose --profile app down`

Скрипт `docker/postgres-init.sql` выполняется только на пустом томе PostgreSQL. Если том создан до появления `recruitment`, `client` или `comment`, создайте базы вручную:
`docker compose exec postgres psql -U postgres -c "CREATE DATABASE recruitment"` (и `client`, `comment`) и выдайте роли `recruiting_app` права, как в init-скрипте (либо пересоздайте том: `docker compose down -v`).
(`-v` дополнительно удалит данные). Учётные данные и `SERVICE_TOKEN` в `docker-compose.yml` - только для
локального просмотра. Без профиля `app` поднимаются лишь PostgreSQL и Redis (их используют тесты).

## Тесты

```sh
docker compose up -d --wait
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace             # юнит, интеграционные (реальный PostgreSQL и Redis), e2e
```

Интеграционные тесты создают временные БД и подключаются ролью без `BYPASSRLS`, поэтому проверяют
реальную изоляцию. Адреса по умолчанию: `TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres`,
`TEST_REDIS_URL=redis://127.0.0.1:6379`. Браузерные тесты и `cargo leptos build` требуют установленных
Chrome и cargo-leptos; первый запуск e2e собирает все приложения (несколько минут).

## Запуск сервисов вручную

Каждый сервис настраивается переменными окружения.

| Сервис | Обязательные | Необязательные |
|---|---|---|
| identity | `DATABASE_URL`, `ADMIN_URL`, `SERVICE_TOKEN` | `MIGRATION_DATABASE_URL`, `JWT_PRIVATE_KEY`, `ACCESS_TTL_SECS`, `TENANT_CACHE_TTL_SECS`, `LISTEN_ADDR` |
| candidate | `DATABASE_URL`, `IDENTITY_JWKS_URL`, `SERVICE_TOKEN` | `MIGRATION_DATABASE_URL`, `LISTEN_ADDR` |
| client | `DATABASE_URL`, `IDENTITY_JWKS_URL`, `SERVICE_TOKEN` | `MIGRATION_DATABASE_URL`, `LISTEN_ADDR` |
| comment | `DATABASE_URL`, `IDENTITY_JWKS_URL`, `SERVICE_TOKEN` | `MIGRATION_DATABASE_URL`, `LISTEN_ADDR` |
| recruitment | `DATABASE_URL`, `IDENTITY_JWKS_URL`, `SERVICE_TOKEN`, `CANDIDATE_URL`, `CLIENT_URL` | `MIGRATION_DATABASE_URL`, `LISTEN_ADDR` |
| admin | `DATABASE_URL`, `IDENTITY_URL`, `SERVICE_TOKEN` | `MIGRATION_DATABASE_URL`, `JWT_PRIVATE_KEY`, `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `LISTEN_ADDR` |
| bff-crm | `IDENTITY_URL`, `CANDIDATE_URL`, `RECRUITMENT_URL`, `CLIENT_URL`, `COMMENT_URL` | `REDIS_URL`, `COOKIE_SECURE`, `BASE_DOMAIN`, `SESSION_TTL_HOURS`, `CORS_ORIGINS`, `LISTEN_ADDR` |
| bff-admin | `ADMIN_URL` | `REDIS_URL`, `COOKIE_SECURE`, `SESSION_TTL_HOURS`, `CORS_ORIGINS`, `LISTEN_ADDR` |
| web-crm / web-admin | `BFF_URL`, переменные `LEPTOS_*` | `BFF_PUBLIC_URL` |

- Миграции применяются при старте от `MIGRATION_DATABASE_URL` (владелец схемы), а запросы обслуживаются
  от `DATABASE_URL` — роли без `BYPASSRLS` (в compose это `recruiting_app`).
- Без `JWT_PRIVATE_KEY` сервис генерирует временный ключ: токены перестают действовать после перезапуска.
- Браузер ходит в BFF **напрямую** (после первой отрисовки), а сервер фронтенда при SSR — по внутреннему адресу:
  `BFF_URL` (внутренний, для SSR) и `BFF_PUBLIC_URL` (адрес для браузера, по умолчанию равен `BFF_URL`; сервер кладёт его
  в страницу мета-тегом `bff-url`). BFF разрешает такие запросы только источникам из `CORS_ORIGINS` (адреса фронтенда через
  запятую, `*` запрещён; пусто — CORS выключен). Cookie сессии `SameSite=Lax` уходит с запросом, только если фронтенд и BFF —
  один «сайт» (оба на `localhost` либо поддомены одного домена; порт не учитывается); иначе нужен общий родительский домен
  или reverse proxy, при котором `BFF_PUBLIC_URL` указывает на тот же origin. Локально: web-crm `:3000` ↔ bff-crm `:8081`,
  web-admin `:3010` ↔ bff-admin `:8082`.
- `candidate` проверяет токены по ключу identity (`IDENTITY_JWKS_URL`, например `http://127.0.0.1:8080/.well-known/jwks.json`): ключ загружается лениво и перечитывается при смене, поэтому сервис стартует и без identity (запросы получают 401).
- `COOKIE_SECURE=false` нужен только при работе по http (локально).
- Веб-приложения собираются `cargo leptos build --project web-crm` (и `web-admin`).

## Импорт кандидатов

Файл (`.csv`/`.tsv`, `.xlsx`, `.pdf`) разбирается **в браузере** crate'ом `crates/candidate-import` (Rust, без `regex`
и без проверки CRC у XLSX): таблицы — с автоматическим сопоставлением колонок, PDF — простые шрифты (WinAnsi и
`Differences`), а при нечитаемом тексте предлагается вставить его вручную. На сервер уходят только проверенные строки
пакетами по 200 (`POST /persons/import`, до 500 в запросе): плохие строки отклоняются с причиной, «тот же человек»
(email → телефон → имя) дополняется только пустыми полями, дублей нет; отклики на вакансию создаются
`POST /applications/batch`. Лимиты: файл до 5 МБ, до 2000 строк.

## Аналитика

`GET /analytics?days=` (7…365, по умолчанию 90) считает метрики по запросу чистыми функциями
(`services/recruitment/src/domain/analytics.rs`): воронка идёт по **пройденным** этапам (у событий истории хранится
этап, миграция `0002` заполнила его для старых записей), поэтому отказанные после интервью остаются в воронке;
медианы срока найма и времени до первого касания, источники по конверсии в «Интервью HR», отклики по неделям
(понедельник, UTC), нагрузка на вакансии.

## Палитра команд и горячие клавиши

В шапке клиентского приложения: строка поиска, «+ Добавить» (кандидат, вакансия, импорт), «Разбор» и «?». Клавиатура: `Ctrl K` (или строка поиска) открывает палитру — поиск по действиям, разделам, вакансиям и людям. `G` и затем `T`, `V`, `O`, `C`, `A` — переход по разделам, `/` — поиск по кандидатам, `T` — разбор откликов, `I` — импорт, `?` — шпаргалка. Клавиши не срабатывают в полях ввода; действия, меняющие данные, недоступны роли `viewer`. В списке «Отклики»: `J`/`K` — курсор, `Enter` — панель человека, `X` и `A` — выделение, `E`, `R`, `M` — действия над выделенными, `1…8` — перевод на этап. В панели: `E`, `R`, `S`, `N` и цифры. `Esc` закрывает по одному слою: окно, форму, панель, выделение. Код: `apps/web-crm/src/palette` и `apps/web-crm/src/funnel/keys.rs` (разбор клавиш и реестр команд — чистые функции с юнит-тестами).

## Тема

Кнопка ◐ в шапке (и команда палитры «Переключить тему») меняет светлую тему на тёмную и обратно. Выбор хранится в браузере (`localStorage`, ключ `theme`) и применяется до первой отрисовки; пока выбора нет, действует тема системы. Код: `crates/ui-kit/src/theme.rs`.

## Заказчики

Заказчик — отдельный ограниченный контекст (`services/client`, БД `client`): название (уникальное в организации),
примечание, архив; у заказчика сколько угодно контактных лиц (ФИО, должность из справочника организации, email,
телефон). Вакансия привязывается к заказчику (`client_id` обязателен для новых вакансий) и необязательно к его
контакту; прежние текстовые поля «подразделение» и «нанимающий менеджер» из API убраны, значения в БД остались.
Воронка получает заказчиков и контакты по ленте изменений `GET /internal/tenants/{id}/client-changes` — так же,
как людей из `candidate` — и проверяет ссылки по своей проекции. Раздел «Заказчики» в интерфейсе: список, карточка с
контактами, справочник должностей.

## Комментарии

Блок «Комментарии» есть на карточке заказчика, в карточке вакансии, в карточке кандидата и в панели человека.
Комментарий — текст до 5000 символов с автором и временем; автор правит и удаляет свои комментарии, владелец
организации удаляет любые, `viewer` только читает. Сервис `comment` не проверяет, что объект существует (ссылка по
типу и идентификатору); имя автора он берёт из access-токена (поле `name`, которое выпускает identity).

## Воронка и данные людей

`recruitment` хранит вакансии и отклики, а людей (имя, источник, город, ожидания, навыки, стаж) держит у себя
**проекцией** — копией, нужной для фильтров, поиска и сортировки одним SQL-запросом. Проекция обновляется при
каждом чтении по ленте изменений `candidate` (`GET /internal/tenants/{id}/person-changes?after=`, сервисный
токен): кандидат создан или изменён — воронка видит это сразу, а при недоступности `candidate` отвечает по
последним известным данным (заголовок `x-people-stale: true`). Удаление кандидата удаляет его отклики.
Письма, приглашения на интервью и передача вышедшего в кадровую систему **имитируются записью в историю
отклика** — реальных интеграций нет. Подробности — в `openspec/changes/add-hiring-funnel/design.md`.

## Структура сервиса

Каждый сервис — один crate с модулями `domain` (агрегаты и инварианты), `application` (сценарии и порты),
`infrastructure` (PostgreSQL, HTTP-клиенты), `api` (axum-маршруты, OpenAPI на `/openapi.json`).
Новый сервис копирует эту форму.
